# 构筑平衡：理论预算曲线与实际对局数据

固定预算实验已实现；本文中的真实对局统计仍是方案，目前没有采集或上传玩家对局数据。两条路径互补：确定性模拟帮助定位机制与比较同预算构筑；真实数据用于发现命中率、操作成本、关卡和多人协作造成的偏差。最终调整需要人工复核，不能仅凭单一指标自动改卡。

## 运行已有实验

执行 `npm ci` 后运行 `npm run balance:report`，打开 `public/balance/index.html`。GitHub Pages 自动构建时也会重新运行实验，报告位于 [在线伤害曲线](https://what20360.github.io/prism/balance/)。构建时生成的文件不作为源码提交，避免代码更改后继续展示旧结果。默认配置为 `config/balance-report.json`，可修改预算、预热/测量秒数、种子、构筑、目标坐标、半径和防御。也可以指定独立配置和输出目录：

```sh
npm run balance:report -- --config config/balance-report.json --out /tmp/prism-balance-report
```

报告包括单体和多靶的 SVG 曲线、可展开的价格与购买顺序、JSON 全量结果及 CSV。横轴使用 `log₂(预算+1)`，纵轴是每秒生命损失；多靶另报告各靶和每靶平均。每个预算独立从零按 `opening` 然后循环 `cycle` 购买，首个买不起的卡即停止，余额保留，不跳过或出售。购买使用真实 `buyCard`，前置、互斥、层数及价格变化自动生效。未完成 opening 的构筑不画点；未知卡、非法前置等明确失败。修改价格、卡片、武器或伤害规则后直接重跑即可；如修改导致构筑顺序不再合法，报告会报错，需调整配置而不会静默替换卡片。

核心实验位于 `src/analysis/budget.ts`，每次调用当前 `step()`、武器、地雷与受击结算。玩家固定位置持续开火或放雷，首靶为瞄准/锁定目标；场景无障碍物，敌人固定、不攻击、无盾、无核心且生命足够大，使用场景指定位置和防御；包含命中、弹道、格挡、护甲、抗性及热伤状态，但不强制命中、不计溢出、不模拟技能或实战走位。远距离地雷零伤害是目标不触发雷，不是地雷固有DPS。不同构筑的测试场景完全一致，单体和群体曲线不能混成同一项比较。

默认预热5秒、至少测量30秒；慢速构筑按基础冷却估算延长到至少10个周期，最多1200秒。报告逐项给出实际时长，达到上限仍不足10周期时标记“周期不足”；有限窗口仍有首尾脉冲和子弹飞行误差，不等于严格解析极限。每次输出写入源码基线、源码及配置SHA-256、种子与完整配置。默认9个静止场景、5个固定构筑、6档预算；不是穷举搜索、更不是全局最优，也不能用同预算结果代替同时间实际成长比较。当前未实现随机走位、多种种子的区间估计或真实对局采样。

## 固定预算实验的扩展方向

1. 选定游戏版本、模式、预算、初始棱晶是否计入、构筑购卡顺序；逐级使用当前卡片的价格函数、前置和互斥约束。列出未花完的余额，不用出售退款人为扩大预算。预算序列建议 50、100、200、400、800、1600，也允许用户输入。
2. 用相同初始角色、无额外技能和相同目标场景分别测试弹芯、狙击、电弧、激光及代表性地雷流。区分人工指定构筑、有限搜索结果及搜索范围内的最优结果；不把有限搜索称为全局最优。记录详细购卡序列，确保结果可复现。
3. 报告单体与群体曲线：分别包含无防御、高格挡、高护甲、属性抗性、混合敌群；群体注明目标数量、位置和墙体。电弧共享树节点预算，分叉与衰减按现有引擎计算；激光按脉冲、连续射击与结束后冷却；狙击计入一弹上限与弹道飞行。组内总有效伤害/秒与单位目标有效伤害/秒分别展示，避免目标数量使群伤虚高。
4. 理论上限假设持续命中、目标不移动，计入防御和时间；移动、射程、掩体、命中概率及追踪等实际限制另做模拟场景，不称为理论上限。用固定时长及多随机种子统计均值和区间，预热与测量窗口写明；先比较同金额，再比较同游戏时间下的收益，不能把两者混为一谈。
5. 优先复用核心战斗和卡片结算，通过独立命令生成机器可读数据和图表；给每种武器添加已知场景的回归测试，并保留版本、种子、目标、构筑和实现哈希。单看静态属性乘法不能正确表示格挡、电弧持续供能、穿透及实际攻击周期。

## 真实对局统计方案（尚未实现）

- 服务器端按房间/玩家单独明确选择加入，默认关闭；界面列明字段、用途、存放位置、保留时间和退出方式。不开启时不记录分析数据，不影响对局；不把现有的调试日志当作授权采集。
- 以对局结束或房间结束的聚合记录为主：版本、模式、难度、种子、层数、人数、耗时、结果，武器及卡片等级、经济收支、有效伤害/承伤、治疗、复活、击杀、失败原因，以及目标房选择、完成和退出数量。数据口径明确包括护盾、召唤体、溢出和暂停；资源分配与人数需作为分层条件。
- 最小化数据：不上传按键、轨迹、聊天、访问令牌、房间密码、IP 或稳定设备标识；不需要跨局追踪时只用一次性对局随机标识。聚合优先，服务器管理员设置短保留期、容量限制和删除方式；不将数据公开或自动传给第三方。
- 保存格式有版本及大小上限；采用服务器权威结果，单人游戏不静默上传。断线、崩溃、未完成局和重复上报有明确标记与去重，不作为正常通关率分母。
- 按版本、难度、层数、队伍规模、武器和预算区间分组，展示样本量、分位数、通关/失败与耗时；小样本不做结论。主动选择上传存在自选择偏差，构筑选择也受玩家技能影响，相关性不代表卡片导致结果。

## 实施次序与验收

先用现有固定预算实验建立单体/群体、不同防御的基准；然后以曲线异常为线索安排实际试玩。多人场景和随机走位仍待开发。若仍需要真实统计，先确定数据字段、告知方式、保存及删除策略，再开发默认关闭的服务器聚合记录。数值调整需保留修改前后实验配置、样本量和理由，发布后复核；数据不足时维持假设，不宣称已验证平衡。
