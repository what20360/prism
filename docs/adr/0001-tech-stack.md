# ADR-0001 技术选型：Vite + TypeScript + Canvas2D（零运行时依赖）

- **状态**：已采纳
- **日期**：2026-10-29
- **决策者**：项目负责人
- **影响范围**：全部实现

---

## 背景

PRISM 是一款 2D 俯视角几何风格的地牢 Roguelike，要求：

1. **浏览器优先**，同时保留后续打包到桌面/移动的可能；
2. **逻辑与表现彻底分离**（`core/` 无 DOM、可 headless 测试）；
3. **模块可替换**（渲染器、输入、网络、存储）；
4. **确定性**（固定步长、可回放、为联机留路）；
5. **零外部美术资源**（纯几何绘制）；
6. 单人开发，需要**强类型**与**快速迭代**。

约束：当前环境仅安装 Node 18 / npm 9 / Python 3.10，无游戏引擎。

---

## 备选方案

| 方案 | 优点 | 拒绝原因 |
|---|---|---|
| **Phaser 3** | 开箱即用：场景、物理、输入、音频 | 场景与物理绑定 DOM 生命周期，难以让逻辑层脱离浏览器；运行时包大；「模块可替换」会退化为「与框架共存」 |
| **PixiJS** | 渲染性能好、生态成熟 | 只解决渲染；仍需自建逻辑层与输入层，最终等价于本方案 + 一个更重的渲染依赖 |
| **Godot 4** | 完整引擎、可视化编辑 | 不满足 Web 优先；逻辑层无法用 Node 直接单测；环境未安装，且会引入引擎特有的资源管线 |
| **原生 JS + Canvas2D** | 依赖最少 | 无类型保障，内容数据（敌人/卡片/关卡）规模一大就会失控 |
| **TS + Vite + Canvas2D（采纳）** | 类型安全、构建简单、逻辑可 headless、渲染可替换 | 需要自己实现循环、碰撞、输入——详见「后果」 |

选择 Canvas2D 而非 WebGL 的理由：本作画面是**少量几何图元**（圆、矩形、线段），2D Context 的绘制成本极低；
WebGL 的批处理优势在这个量级上无意义，反而增加着色器与状态管理负担。渲染器通过接口隔离，未来可换。

---

## 决策

1. **语言**：TypeScript（`strict: true`），所有 `core` 类型显式标注。
2. **构建/开发服务器**：Vite。开发态 HMR，生产态纯静态产物。
3. **渲染**：首发 Canvas2D，封装在 `render/canvas2d/` 内，对 `core` 不可见。
4. **运行时依赖：零**。所有能力（循环、输入、PRNG、校验、音效合成）自行实现或使用 Web 平台 API。
5. **开发依赖**：`vite`、`typescript`、`vitest`、`eslint`、`prettier`。
6. **测试**：Vitest。`core` 单测 + 确定性回放回归 + `core-isolation` 结构测试。
7. **音效**：WebAudio 程序化合成，不引入音频文件与音频库。
8. **内容数据**：`content/*.ts` 常量（类型即校验）+ 手写运行时校验器，不引入 Zod 等库。

## 后果

### 正面

- `core/` 可在 Node 中运行完整一局，规则测试不需要浏览器或画布。
- 渲染器、输入、网络、存储互不影响，替换成本低（requirements 9.3 的可替换点清单因此才成立）。
- 无运行时依赖 → 包体小、无供应链与升级风险、构建产物长期可用。
- 确定性为回放测试与未来的联机同步打底。

### 负面 / 代价

| 代价 | 缓解 |
|---|---|
| 需要自己写固定步长循环、碰撞检测、输入抽象 | 这些都是本作的核心资产，且需求已明确（architecture 5.4） |
| 没有编辑器的关卡设计工具 | 房间模板数据化，先手写；编辑器列为非目标 |
| Canvas2D 在极端弹幕下可能成为瓶颈 | 实体上限（子弹 ≤ 400）+ 图元批处理；必要时换渲染器 |
| 未来若需要 3D 或复杂粒子，需要重写渲染层 | 渲染层已是可替换边界，重写不影响规则 |

### 需要长期守住的边界

- `core/` 一旦出现 `document`、`window`、`canvas`、`fetch`，本决策即失效 → 由 ESLint + 结构测试强制。
- 卡片 `effectFn` 必须是纯函数，否则确定性失效（见 architecture 5.2）。
